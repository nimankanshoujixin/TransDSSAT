# 作物输入空间设计备注

更新时间：2026-05-26

这份备注用于回答一个具体问题：

> 现在要不要把作物种类也设计进输入空间？

## 结论

建议采用：

> **先设计接口，先保留作物 / 品种上下文；实现上先兼容单作物，后续再扩展到多物种。**

## 理由

- 当前项目已经明确会面对不同作物、不同品种的校准 DSSAT。
- 后续多物种扩展如果不预留接口，会连带改动场景 schema、评测 runner、数据导出、模型编码层。
- 现在就把作物种类硬编码成动作空间或不可扩展的单一特征，不划算。
- 但也不应该完全不管作物种类，因为它本来就是场景真实性的一部分。

## 推荐分层

### 1. 场景元数据层

必须保留：

- 作物种类
- 品种名称
- 品种引用
- 遗传参数块

### 2. 模型接口层

建议预留一个 `crop_context` 或同等结构：

- 现在可以先是空实现或单作物默认值
- 后续可挂载 crop embedding、cultivar embedding、品种参数向量

### 3. 动作空间层

- 不要把作物种类放进动作空间
- 作物不是决策动作，作物是场景条件

## 登海605 参数建议

你给的参数：

```text
340.9、1.610、700.0、600.0、10.50、60.00
```

建议先作为：

- 作物种类：玉米
- 品种名称：登海605
- 遗传参数向量：`[340.9, 1.610, 700.0, 600.0, 10.50, 60.00]`
- 参数说明：`missing_details`

在没有拿到参数名、单位和顺序之前，不要擅自解释每个数的生理含义。

## 可接受样例

```json
{
  "作物名称": "maize",
  "作物种类": "玉米",
  "品种名称": "登海605",
  "品种引用": "Denghai605_calibrated_v1",
  "遗传参数向量": [340.9, 1.61, 700.0, 600.0, 10.5, 60.0],
  "参数说明": "missing_details",
  "数据来源": "农业同学校准结果"
}
```

## 对当前工作的影响

当前第一阶段可以继续按单作物先跑通，但接口应提前留好，避免之后为了接入水稻、玉米或其他作物而重构。
