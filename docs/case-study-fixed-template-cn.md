# TransDSSAT Case Study 固定规范模板

## 1. 使用目标

这份模板用于把后续 case study 写成统一格式，默认面向：

- 业务同学
- 农艺同学
- 研发同学

默认不把 case study 写成：

- 纯技术实验日志
- 纯训练配置清单
- 只贴分数、不解释业务含义的结果页

## 2. 固定章节顺序

后续所有 case study，默认按下面顺序写：

1. 标题
2. 开场 callout
3. 场景 / 当前阶段说明
4. 背景条件
5. 模型到底做了什么
6. 带来了什么结果
7. 和参考对象相比的 tradeoff
8. 需要农艺 / 业务重点判断什么
9. 这份 case 想帮助回答什么
10. 附录

## 3. 标题规范

标题默认采用下面几类：

- `农艺复核样本：<模型名> 单场景决策`
- `连续决策值现状汇报样本`
- `<主题> case study`

要求：

- 标题里直接说清楚对象
- 不要用过于抽象的命名
- 如果不是正式结果，标题里不要暗示“已验证优于基线”

## 4. 开场 callout 规范

第一屏必须先放一个 callout，明确三件事：

1. 这份材料给谁看
2. 这份材料不是什么
3. 它真正想帮助判断什么

推荐句式：

> 这份材料是给业务、农艺和研发协同看的，不是新的训练战报。  
> 目的只有一个：把当前这个 case 里最值得判断的业务含义说清楚。

## 5. 背景部分必须覆盖什么

如果是单场景 agronomy case，至少要交代：

- 场景编号
- 地点 / 作物 / 品种
- 播种日期
- 天气年份 / 类型
- 土壤类型
- 初始水分 / 初始土壤氮
- 水肥预算
- 管理目标

如果不是单场景 agronomy case，而是阶段性接口 / 语义 / 新线状态汇报，至少要交代：

- 当前线名称
- 当前任务状态
- 当前已完成内容
- 当前权威基线
- 当前阻塞点

## 6. “模型到底做了什么”这一节怎么写

这一节必须让非研发同学也能快速看懂，优先展示：

- 动作是什么
- 动作在什么时候发生
- 总共发生几次
- 是否有明显的农业直觉风险

推荐优先使用：

- 表格
- 简短列表
- callout
- 双栏 grid

不要在这一节堆：

- 大段代码
- PPO 公式
- 内部 tensor 名字
- 过细的训练实现细节

## 7. “结果”这一节的强制边界

后续所有 case study，必须明确区分下面三类内容：

| 类型 | 是否可以当正式结论 |
| --- | --- |
| 正式训练结果 | 可以 |
| dry-run / CPU-safe 样本 | 不可以 |
| 手工构造或接口演示样本 | 不可以 |

强制规则：

- 如果没有正式 checkpoint / metrics，就必须明确写“没有正式分数”
- 不能把示例值写成正式成绩
- 不能把 CPU-safe 接口样本写成农业推荐方案

## 8. 对比 section 的固定问法

一旦有对比对象，默认至少比较：

- 当前方案 vs heuristic
- 当前方案 vs 当前权威 AI baseline

推荐对比指标：

- 产量
- 总灌溉
- 总施氮
- 操作次数
- 氮淋失 / 排水
- 总分或 reward gain

并且必须补一句“这个 tradeoff 在业务上到底意味着什么”。

## 9. “请重点判断什么”这一节必须存在

每份 case study 都必须落到一组可判断问题，而不是只展示结果。

推荐问题类型：

1. 这个动作节奏像不像真实田间管理。
2. 这个投入水平是否过于激进。
3. 这个策略是在省投入，还是在真正提高效率。
4. 这个结果是否符合当前业务目标。
5. 如果业务更强调稳产，这个方案是否还能接受。

## 10. 固定写作口径

写作时默认遵守以下口径：

- 先说边界，再说亮点
- 先说当前权威结果是谁，再说新线处于什么阶段
- 用绝对日期，不只写“今天 / 当前 / 最新”
- 对业务同学讲 tradeoff，对研发同学讲 trust boundary
- 不把“更高分”直接等价成“更合理”

## 11. 交付前强制检查

每次交付 case study 前，必须完成下面两项验收；任一不满足都算阻塞错误，不能交付：

- 中文编码验收：本地 Markdown 和飞书文档都必须确认中文正常显示；如果出现 `????`、乱码、字符丢失，就必须先修复再交付
- 单场景 agronomy case 附录验收：附录里必须包含**全季完整天气表**，不能只放月度汇总、抽样窗口或局部天气片段

## 12. 推荐版式

默认沿用下面这些元素：

- `#` 标题
- `##` 固定章节
- 顶部 callout
- 关键表格
- 必要时双栏 `grid`
- 文末附录

推荐节奏：

- 先总后分
- 每节 1 个核心问题
- 每张表只服务一个判断点

## 13. 最小骨架

后续新 case 可以直接从下面骨架复制：

```md
# <标题>

<callout emoji="🌾">
**这份材料是给谁看的，不是什么。**

目的只有一个：<一句话说明这份 case 想帮助判断什么>。
</callout>

## 1. 这个 case / 这条线现在是什么情况

## 2. 背景条件

## 3. 模型到底做了什么

## 4. 带来了什么结果

## 5. 和参考对象相比是什么 tradeoff

## 6. 请农艺 / 业务重点判断这些问题

## 7. 这份 case 想帮助回答什么

## 附录 A. 全季完整天气

## 附录 B. 额外明细
```
